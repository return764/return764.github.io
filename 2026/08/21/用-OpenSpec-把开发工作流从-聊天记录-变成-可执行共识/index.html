开发工作流：OpenSpec 与快速实现的双路径实践

Tao Yu
2026-08-21
开发工作流 › OpenSpec
AI 协作, OpenSpec, 快速实现, 软件工程

我现在的开发流程只有一个目标：既不为了速度牺牲长期上下文，也不为了流程拖慢小改动的交付。

为此，我会把需求分到两条路径：OpenSpec 常规实现处理大变更和需要明确决策的需求；快速实现处理小功能与紧急修复。两者共享同一份项目上下文，最终都要把已经发生的改变同步回文档。

这不是“正式流程”和“随便改改”的对立。快速实现是缩短了前置流程，而不是取消了质量和知识沉淀；OpenSpec 则在复杂度较高时，把讨论变成可执行、可验证的共识。

两条路径，共用一个起点

无论走哪条路，开始前都先读取项目上下文：例如 CONTEXT.md、AGENTS.md、README.md、架构说明和数据模型文档。用户输入描述的是“这次想要什么”，项目文档则说明“这里原本是什么样、哪些约束不能破坏”。

如果只根据一句需求直接写代码，AI 或开发者很容易做出局部正确、整体不一致的实现。上下文是两条路径共同的护栏。

维度 OpenSpec 常规实现 快速实现
适用需求 跨模块、大功能、有明显设计取舍 小功能、明确 bug、紧急修复
前置工作 形成 specification doc 和可读计划 直接确认目标、范围与现有约束
实施节奏 按 spec 和任务逐项推进 尽快完成最小正确改动
交付后的动作 归档 specification，成为后续事实来源 同步变更文档，并更新归档规范
主要收益 降低沟通和返工风险 降低交付等待和流程成本

判断标准不在需求的大小，而在不确定性和影响面：这次改动是否会改变用户行为、接口契约、数据结构或其他模块的假设？如果会，而且答案并不显然，就应该走 OpenSpec。

路径一：OpenSpec 常规实现

常规路径适合“先想清楚，再放心写快”的需求。图中的主线是：

先写 specification doc

我会先把这次变更写成一个 specification doc。它不应该只是实现待办，而要回答下面几件事：

  • 为什么现在要做这件事；
  • 本次明确要做什么，以及不做什么；
  • 用户或系统可观察到的行为如何变化；
  • 哪些兼容性、性能、权限或数据约束必须保持；
  • 哪些关键方案需要做取舍。

例如，“为订单列表增加筛选”还不够清楚。规范应进一步明确：筛选条件是否写入 URL、刷新后是否保留、没有结果时显示什么、旧链接是否仍然可用。这些才是可以被实现和验收的约束。

用 readable plan 承接讨论

图中的 readable plan doc 是一个面向人阅读的计划：它可以承接其他轮对话、用户补充与评审反馈，也可以由 specification 生成初稿，再反过来 refine specification。

这个双向关系很重要。计划不是一次性批准后就冻结的清单；当用户补充优先级或发现遗漏场景时，先更新可读计划和规范，再让实现跟上。这样不会出现“代码做了一套、文档说另一套”。

按可验证的任务实现

实现阶段不再把目标写成“完成筛选功能”，而是拆成独立可检查的动作：

每完成一项，都回到 specification 中的场景验证。规格负责说明“正确是什么”，任务负责说明“下一步做什么”，代码和测试负责给出“已经做到”的证据。

归档让规范成为 source of truth

发布或完成验收后，归档这次 specification，并将应长期保留的结论同步到项目主文档。归档的意义不是把文件移进一个目录，而是让下一轮工作可以直接获得可靠上下文：已有行为、做过的取舍和不能轻易打破的约束。

这也是 OpenSpec 在长期项目中最有价值的地方：它把一次变更留下的经验，变成之后的事实来源，而不是散落在 PR、聊天记录或某个人的记忆中。

路径二：快速实现

快速实现适合目标清晰、影响局部、可以迅速验证的改动。它的路径更短：

这里“快”的重点是跳过不必要的方案阶段，而不是跳过理解、测试和同步。一个明确的空状态文案修复、已有接口上的小字段展示、能稳定复现且修复范围清楚的 bug，都可以走这条路。

快速实现也有边界

我会在动手前用三个问题做一次快速判断：

  1. 目标是否足够明确，可以一句话说清验收条件？
  2. 是否只影响一个局部模块，并且不改变接口、数据或核心业务规则？
  3. 是否能用已有测试或一个清楚的手工场景验证？

三个答案都是“是”，通常可以直接实现。只要其中一个答案变成“否”或“还不确定”，就应切回 OpenSpec 路径。快速实现最危险的时刻，就是小改动在过程中长成了设计问题。

代码和变更文档必须同步

快速路径没有独立的 specification 起草阶段，因此更不能遗漏收尾。代码完成后，立即把用户可见的变化、配置变化、使用方式或已知限制同步到 change docs；若该改动改变了已有规范，也要更新相应的 archived specification。

图中 code 与 change docs 的双向箭头，代表一个简单原则：文档不是代码写完后的装饰。实现时发现说明不准确就改文档；文档约束发生变化就重新检查实现。

什么时候该切换路径

选择错误路径的代价并不对称：把小改动走完整 OpenSpec，主要损失一点速度；把有风险的变更当作快速实现，往往会带来返工、兼容性问题和上下文丢失。

场景 建议路径 原因
修正明显的展示文案或样式 快速实现 影响范围小，验收直接
修复可稳定复现、根因明确的局部 bug 快速实现 已知问题与修复边界清楚
增加跨页面、跨服务的新功能 OpenSpec 需要先对行为和边界达成一致
修改 API、数据库结构或权限模型 OpenSpec 兼容性和回滚策略需要设计
需求在实施中不断出现新问题 切换到 OpenSpec 说明原先的不确定性被低估

我宁愿把“中途切换到 OpenSpec”看成一次及时校正，而不是流程失败。能在代码扩散之前补足规格，通常已经省下了后面的返工。

和 AI 协作时怎么使用这两条路径

AI 很擅长在边界明确时快速产出代码、测试和文档，但它不能替项目做未经声明的产品与架构决策。因此我会先明确告诉它当前走哪条路径。

走 OpenSpec 时，提供需求、项目上下文、已确认的范围与非目标、相关行为场景和当前任务，让 AI 先帮助补全计划或规范，再实施。走快速实现时，则明确限定改动范围、验收标准和禁止触碰的模块，并要求它在完成后同步 change docs。

无论哪种路径，代码审查都可以回到同一个问题：这次改动满足了什么行为，依据是什么，相关文档是否已经同步？

总结

OpenSpec 与快速实现不是二选一，而是一套有弹性的开发工作流：

  • 大变更先把共识写成 specification，让规范指导实施，并在归档后成为后续上下文；
  • 小改动快速交付，但保留对项目上下文、测试和文档同步的要求；
  • 当不确定性增加时，随时从快速实现切换到 OpenSpec。

这样既能保留快速迭代的手感，也能让每一次重要变更都留下可追溯、可复用的依据。
